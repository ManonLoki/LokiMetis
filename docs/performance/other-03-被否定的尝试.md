# OTHER-03 被否定的尝试（别重蹈覆辙）

调优里，**知道什么没用**和知道什么有用一样值钱。下面是这次试过又撤销的东西。

## 1. 大读取后手动归还分配器空闲页 —— 反而更糟

- 想法：读完 5 万条数据后，调用 `malloc_zone_pressure_relief`，把空闲页还给系统，footprint 应该下降。
- 做法：加在扫描、查询、后台摘要结束处，5 秒节流。
- 实测（同一二进制，用开关开关，各 4 次，100 秒后）：
  开启 178 / 203 / 183 / 241 MB，关闭 126 / 148 / 103 / 123 MB。**开启后明显更高。**
- 结论：已删除，不保留任何"凭直觉的回收调用"。

## 2. 可绘制纹理数 3 → 2 —— 没有可测收益，且有卡顿风险

- 想法：每个窗口少一块整窗大小的 IOSurface，约省 21 MB。
- 实测：IOSurface 区域确实少了（均值约 36 对 51 MB），但整应用 footprint 中位数 147 对 151 MB，**差别小于波动**。
- 风险：只有两块时，GPU 慢或高刷新率下 `nextDrawable` 可能阻塞主线程，而我们没有逐帧延迟测量。
- 结论：已撤销，恢复三块。

## 3. 把 UI 观察循环直接停掉 —— 没做

想直接去掉"每 10 秒重新查概览"，但这个定时器可能在兜底某些外部变化。
更稳的做法是让后端变便宜（CPU-02），而不是在界面层把它拿掉。

## 4. 直接停掉显示器节拍线程 —— 没做

必须先补齐所有重新唤醒的路径（脏了、动画、resize、重新可见、可访问性激活），才能停。
没有强收益证据前不做。

## 5. 把累加改成乘法 —— 差一个舍入

`n 次累加` 改成 `乘以 n`，在特定浮点输入下会差 1（127 对 128）。别这样"优化"。

## 怎么避免重复犯错

- 每个"想象中的收益"，都要有受控 A/B；
- 单项改动如果整体看不出收益，就别带着风险上线；
- 在文档里写下"试过什么、结果是什么"，下次不用重试。
