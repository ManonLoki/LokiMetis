# MEM-01 峰值：数据在谁手里、被复制了几份

## 先说结论

读一大批数据（比如 5 万条调用）时，内存会先冲高再回落。这个**峰值**取决于：
**同一份数据在同一时刻有几份存活。** 优化峰值，就是顺着数据的"所有权"找出多余的那几份。

## 怎么量（确定、可重复）

整应用的 footprint 运行间波动能到 ±40 MB，会盖住这类小改动。所以我们写了一个**计数分配器**示例：
记录 Rust 堆"同一时刻存活字节"的最高点。

```
cargo run --release -p loki_metris_core --example alloc_peak
```

输入是 5 万条贴近真实形状的调用（本身约 34 MiB）。每次结果几乎一样，才能比较。

## 找到的四处多余副本

### 1. canonical 去重：多出一倍

原来去重是"逐条插入 `BTreeMap<String, UsageCall>`"：
- map 里每条调用的**键是 ID 的又一份克隆**；
- 另一张"置信度表"里**再克隆一份 ID**；
- 最后 `into_values().collect()` 又分配一个**第二份结果向量**，此时 map 还没释放。

改成"按 ID 排序后逐组折叠"：没有带键副本，也没有置信度表。
**峰值 +35.23 MiB → +15.26 MiB。**
为了确保结果完全一样，我们把旧实现留在测试里当"参照"，用 300 组随机输入（含重复、同值、冲突、置信度升级）比对，逐字段一致，警告顺序也一致。

### 2. 联合视图的"每条调用来自哪个 Agent"：每条存一份副本

原来是 `BTreeMap<调用ID, 来源>`，每条都复制一份 ID 和 `source_version` 字符串。
但调用 ID 本来就带 `all-<agent>-call-` 前缀，所以只需要一张"前缀 → 来源"的小表。
图表页的 Agent 维度原来还要临时再建一张完整的"ID → Agent"映射，也一并去掉。
**联合合并：峰值 +22.19 → +16.11 MiB，结束后常驻 +14.56 → +8.49 MiB。**

### 3. 读 SQLite 之后立刻释放原始行

数据库返回的每一行解码成领域对象后，原始列值没必要再留着。改成"消费"结果行，当前行解码完立刻销毁。
在固定的 2 万行夹具上，新进程生命周期峰值约少 10.6 MiB（13.9%）；注意这只缩短"两份数据共存"的时间，不是流式读取。

### 4. 增量扫描里别 clone 整批快照

旧代码在写库阶段把整批兼容快照 `clone` 一遍，原对象还要活到函数返回。改成 `mem::take` 转移所有权，用完立即释放。

## 不要被误导

- **`String::clear()` 不释放容量。** 长度变成 0，但原来的 Base64 缓冲还占着。需要真释放时用 `String::new()` 替换。
- **256 条只是每批长度，不是内存上限。** 整文件解析的结果仍然整个在内存里。
- **改了也要诚实标注"没测整应用"。** 这些堆上的节省，在整应用 footprint 里看不出独立效果（运行间波动更大）。
  整应用上看得到的收益主要来自 [CPU-02](cpu-02-没变就别重读.md) 的缓存：缓存让"大批量读取"几乎不再反复发生。
