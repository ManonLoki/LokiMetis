# CPU-02 周期性重读：用文件戳判断"没变"

这是这次调优里**收益最大**的一项。

## 问题

应用有几个"每隔一段时间就刷新一次"的地方：

- 后台"今日用量"摘要，桌宠可见或通知开启时**每 30 秒**算一次；
- 概览页开着时**每 10 秒**重新查一次；
- WorkBuddy 的对话日志，每次摘要都会**完整重读约 136 MB 的 JSONL**。

每次刷新都做同样的事：把保留期内全部调用（本机约 5 万条）从 SQLite 读出来、重新给 ID 加前缀、
排序、去重、再聚合出 6 个时间窗口。可数据**其实没变**。

## 怎么发现的

对"看起来很闲"的应用连续采样，把"等待"的线程排除，发现 `today::load` 这条路径占掉了最大的一块后台 CPU：
优化前 45 秒内这个函数相关的采样点是 355 个，里面 `read_project_usage`（读 WorkBuddy 日志）144、
联合快照构造 173、读 SQLite 149。

## 怎么修的

核心思路：**用一个便宜的"没变"判据，没变就复用上次的结果。**

判据是"文件戳"：文件长度、修改时间，在 Unix 上再加设备号、inode、状态变更时间。这几个都一样，就认为内容没变。

1. **WorkBuddy 日志**：每个文件解析后，连同它的文件戳一起缓存。下次文件戳没变，就直接用上次的结果。
   但**每轮还是会重新列目录、打开每个文件、检查它是不是符号链接**，所以文件被删、换名、权限变了，照样报错。
   只缓存"完整落在字节和条数预算内"的文件；超过 10 万条后新文件不再缓存。
2. **索引汇总**：键是 `所选 Agent 的 SQLite 主文件和 -wal 文件的文件戳 + 覆盖报告 + 当前民用日`。
   键没变，就复用上次算好的 6 个窗口汇总，只把观测时间换成现在。
   - 只缓存有界的窗口汇总、键和 Agent 分量，**不缓存那 5 万条调用本身**；缓存仍占内存，但不保留整批调用。
   - 如果发现 `-journal` 文件存在，说明正在写事务，这时既不用也不存缓存。
   - 读之前和读之后各取一次键，两次不一致就不保存，避免把"写到一半"的数据当稳定结果。
   - 跨天、索引被扫描改写、覆盖状态变了，缓存都会立刻失效。

## 效果

隔离环境里（5 万条合成数据，120 秒）：

- 稳态 CPU：旧约 3.8 秒，新约 0.6 秒（约 6 倍）。
- 同一个二进制里把索引缓存关掉：footprint 中位数从 147 MB 回到 189 MB，累计 CPU 从 7.4 秒回到 8.8 秒——
  说明这一项是整体收益的主要来源。

## 别踩的坑

- **只缓存"便宜且小"的结果。** 缓存 5 万条调用会把内存问题换成另一种内存问题。
- **没变不等于永远不用重读。** 文件内容读到一半出 I/O 错误，对没变的文件就不会再发现了；这是有意的取舍，已写入文档。
- **别忘了时间相关的字段。** 复用结果时，"观测时间"必须换成这一轮的时间，否则界面会显示过期。
- **缓存键要包含所有会影响结果的东西**：文件戳、覆盖报告、民用日、Agent 选择。漏一个就会出错。
  怎么避免出错，见 [OTHER-01](other-01-缓存怎么做才不出错.md)。
