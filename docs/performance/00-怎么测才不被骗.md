# 00 怎么测才不被骗

性能优化最容易犯的错，是"改完觉得快了"。这篇讲怎么测，才能不自己骗自己。

## 一句话原则

**先弄清楚花在哪，再改；改完要拿同样的条件对比，而且要重复多次看中位数。**

## 三类工具，各管一段

| 想知道什么 | 用什么 | 注意 |
|---|---|---|
| 程序在哪段代码上忙 | `sample <pid> <秒> <毫秒> -file out.txt` | 一次采样只能看"热点在哪"，不能直接换算成 CPU 百分比 |
| 一段时间一共用了多少 CPU | `ps -o time= -p <pid>` 前后相减 | 这是累计 CPU 秒，最直白，也最难骗人 |
| 内存占用 | `footprint <pid>`（看 `Footprint` 和 `phys_footprint_peak`） | 看"当前值"和"历史峰值"，两个都要记 |
| 空闲唤醒频率 | `top -l 3 -s 6 -pid <pid> -stats pid,cpu,idlew` | `idlew` 越小越好，对比同一时长的增量 |
| 应用自己的堆到底多大 | `heap <pid> -sortBySize`、计数分配器（见 MEM-01） | 区分"应用堆"和"系统映射"，见 MEM-02 |

## 怎么做对比实验（A/B）

1. **同一份数据、同一台机器、同样的运行时长。** 我们用一份合成的 5 万条调用数据，每次运行 120 秒后取值。
2. **新旧构建交替跑。** 旧、新、旧、新……不要先把旧的跑完再跑新的，机器状态会漂移。
3. **每组至少 5～6 次，看中位数，别只看平均。** 离群值很常见（我们遇到过一次 464 MB 对 180 MB 左右）。
4. **单项归因只改变一项。** 可以在同一二进制内用开关作消融对照，检查这一项的贡献；历史测量特性见 OTHER-04。
5. **完整版本前后比较使用真实旧提交。** 不能把只关闭一个优化的新版本称为完整旧版本，否则其它改动仍会混入。

## 容易被骗的地方

- **只看一次的总 CPU。** 前 60 秒有启动扫描，每次都不一样。比较稳态要用"区间增量"。
- **拿 `sample` 的采样点数当 CPU 占比。** 采样点数只能说明"这个函数在样本里出现了多少次"，不能乘出 CPU 百分比。
- **前台/后台。** 被遮挡的窗口可能根本没在画。见 UI-04。
- **进程年龄、窗口大小、有没有桌宠** 都会影响结果。对比时要保持一致，写文档时要把条件写出来。
- **把"没观察到"当成"不存在"。** 一次 5 秒采样没看到某个函数，不等于它从不执行。
- **多个改动合在一起的效果，不要拆开吹。** 合计效果是真的，但每项贡献多少要单独做对照才知道。

## 写结论的规矩

- 数字后面一定写条件：哪台机器、什么构建、数据多大、跑多久、几次。
- 没测过的就写"没测"，不要用推断顶替。
- 效果分三档说：**实测到的**、**只在受控微基准里看到的**、**只是推测**。
