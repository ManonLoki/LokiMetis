# MEM-03 图片、预览和原始字节

## 不同"形态"的图片，内存是分开算的

同一张图片在程序里有好几种形态，各占各的内存：

1. **压缩文件字节**（PNG/GIF 原文件）；
2. **解码后的像素**（可能比原文件大几十倍；一张 512×512×120 帧的 APNG 文件只有约 264 KB，解码后大得多）；
3. **GPU 纹理 / 图集**；
4. **旧场景缓存**（回放用）。

文件大小预算（比如单图 32 MiB、总快照 128 MiB）**只约束第 1 种**，管不住第 2、3、4 种。

## 原生图库：别给原生界面生成 Base64 副本

以前给原生目录也生成了 `data:` URL（Base64）。现在原生目录只放 id、文件名、格式、计数，
原始字节另外用 `Arc<[u8]>` 持有。这条路径上的编码工作和编码副本都没了。

注意：完整的 `preview` 接口仍然要真的做 Base64，不能为了省事把 image 字段清空；测试用线程局部计数验证"原生元数据零编码"。

## 皮肤预览：按目录内容退役，别每次离页清全部

- 预览的**编码字节、解码像素、窗口图集、旧场景**是不同所有者，只替换其中一个不能证明别的也释放了；
- 采用新目录时，以新目录里所有内容 ID 为"保留集合"，不在里面的才退役；
- 相同字节的新对象、元数据变化、多卡片共享都继续复用；
- 失败的和过期的异步回执要保持原目录不动。

## 小坑：`String::clear()` 不还容量

长度变 0，但原 Base64 的缓冲区仍占着。交付一个"空字段"时用 `String::new()` 替换。
