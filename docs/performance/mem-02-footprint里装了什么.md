# MEM-02 footprint 里到底装了什么

## 先别慌：一个空应用就有 100 多 MB

我们测过一个什么数据都没有的新实例，`footprint` 大约 150 到 170 MB，启动瞬间的峰值 270 多 MB。
但**应用自己的堆只有约 29 MB**（`heap -sortBySize` 看到的存活对象）。其余是什么？

## 大头不是我们的堆

用 `MallocStackLogging=1` 启动，再 `malloc_history <pid> -allBySize`，最大的几笔分配其实都是**系统文件映射**：

| 来源 | 大小 | 是什么 |
|---|---|---|
| `Assets.car` | 约 117 MB | 系统 UI 资源目录（CoreUI） |
| Metal 着色器缓存 | 约 96 MB | 系统 Metal 编译缓存 |
| 字体文件 | 约 78 + 61 MB | 系统字体解析映射 |
| ICU 数据 | 约 36 MB | 系统文本数据 |

这些映射的地址空间大小不等于 physical footprint；不能将表中大小相加当作进程实际负担。本轮没有单独验证减少这些系统映射的方案。

## 另外几块

- **IOSurface（约 40～60 MB）**：窗口的可绘制纹理（`CAMetalLayer` 的缓冲）。每个窗口 3 块整窗大小。见 [GPU-03](gpu-03-帧调度和可绘制纹理.md)。
- **IOAccelerator（约 20～30 MB）**：GPU 资源。
- **Malloc Large（empty）**：已释放但分配器还没还给系统的大块。
- **Malloc Small 的 "reclaimable"**：系统随时可回收的空闲页，不一定算进 footprint。

## 几个指标别混着读

| 指标 | 含义 | 不能推出 |
|---|---|---|
| `Footprint`（当前值） | 系统对进程当前内存负担的记账 | Rust 活对象总量 |
| `phys_footprint_peak` | 生命周期最高值 | 现在还占这么多 |
| RSS | 驻留页 | 等于 footprint |
| 虚拟大小 | 地址空间 | 实际占用 |

当前值回落、峰值不降，是正常的。**一张活动监视器截图不能证明有没有泄漏。**
判断泄漏要用同样的操作重复多轮，看回到基线后是否一直往上漂。

## 一个重要教训：手动"归还分配器空闲页"反而更糟

直觉上，大读取之后调 `malloc_zone_pressure_relief` 把空闲页还给系统，footprint 应该降。
我们在**同一个二进制里加开关**做受控 A/B（各 4 次，100 秒后）：

- 开启：178、203、183、241 MB（均值约 201）
- 关闭：126、148、103、123 MB（均值约 125）

**开启后反而更高。** 所以撤销了，没有保留任何回收调用。详见 [OTHER-03](other-03-被否定的尝试.md)。
