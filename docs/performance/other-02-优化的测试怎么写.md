# OTHER-02 测试怎么写才能证明优化没改坏行为

优化最怕的是"变快了，但悄悄改了结果"。这次我们反复用到下面几种测试写法。

## 1. 保留旧实现当"参照"，随机输入对比

重写 canonical 去重时，把旧版本原样放进测试模块，用 300 组随机输入（含重复 ID、同值重复、冲突、置信度升级、
不同来源）对比新旧结果，要求**整个结构逐字段相等**，包括警告的顺序。
适合"算法重写，但输出必须一模一样"的场景。

## 2. 错误变体（mutant）必须让测试变红

写完测试，故意把实现改坏（比如缓存键忽略文件戳、判据恒为真），确认对应测试**会失败**。
如果改坏了测试还是绿的，说明测试没有分辨力。

## 3. 冻结旧算法当"像素 oracle"

动画阴影/描边的缓存，不信新算法的自检，而是把**旧的栅格算法冻结在测试里**，
比较完整的 BGRA 字节和切片字段的 `f64` 位值。还要加"错误的乘法写法"作反例（见 CPU-04）。

## 4. 用真实组件，不要只检查内部字段

- 位置保存：要看**到期时间、正式回执、最终存储值**，不能只证明"某个任务字段被清空"；
- 图集：查**真实 tile** 是否还在，别用后端默认返回 false 的 `contains`；
- 通知：用真实宿主、真实 TCP、真实 GPUI 实体观察器，每次读取独立 update，防止通知合并掩盖问题。

## 5. 确定性的内存度量

整应用 footprint 太抖，就写一个**计数分配器**示例，量"同一时刻存活字节的高水位"（见 MEM-01）。
结果可重复，才好比较。

## 6. 测试边界和产品故障要分开记录

旧断言失败时：先搞清楚正式合同、实际观察和失败顺序，再修测试。**不能只是放宽数量、加等待或跳过。**
同样，"测试夹具做不到"（比如 GPUI 的测试窗口没有真实 AppKit 对象）和"产品有问题"要分开记。

## 7. 别重复计数

两个筛选条件重叠的测试结果不能相加。我们写总数时要么只引用一个完整命令的总数，要么注明"含重叠"。

## 8. 隔离测试环境

测试里的数据目录要用临时目录，不碰真实用户数据；需要真实渲染/Metal 的测试，才在本机真实图集上跑。
