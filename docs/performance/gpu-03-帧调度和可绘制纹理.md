# GPU-03 帧调度、显示器节拍和可绘制纹理

## 显示器节拍（CVDisplayLink）

macOS 上每个窗口按显示器刷新率收到"该画下一帧了"的回调。静态窗口也会收到。
之前的做法是：回调进来后由 Core 判断"有没有脏区"，没脏就跳过绘制——但**进入回调本身**（借用 App、处理帧）还是要花 CPU。

### 已做的

给每个窗口一个原子的"需求位"：

- 显示器线程只观察，**有需求才合并一个主线程信号**；
- 主线程拿到回调先消费需求，再进入 Core；回调里新申请的下一帧会保留；
- 动画靠 `request_animation_frame` 续帧，动画结束后窗口静置。

### 保留没动的

静态但仍可见的窗口保留显示器节拍订阅；无需求时省略向主线程派送。窗口被判为 occluded 后退订，显示器最后一个订阅消失时停止对应 display link。这里未实施的是“仍可见但静态时停止节拍”的进一步优化；它需要先补齐脏区、动画、resize、重新可见及可访问性激活的唤醒路径。历史采样没有给出继续停掉可见窗口节拍的强收益证据。

### 要保护的真实需求

- 绘制重入时，要分别合并"强制重绘"和"纯呈现"，不能只记一个重绘标记；
- 高频输入后的一秒呈现期，要按真实截止时间继续安排帧；
- 消费合并信号时，要持有和显示器线程记录时间相同的锁，避免晚到的时间戳留到空闲之后。

## 可绘制纹理数量（drawable count）：试过，撤销了

`CAMetalLayer` 默认让每个窗口持有 3 块整窗大小的 IOSurface（可绘制纹理）。把它改成 2 能直接少一块。

### 我们量到的

- 单独量 IOSurface 区域：改后均值约 36 MB，改前约 51 MB（各 4 次）。
- 整应用 footprint：带补丁中位 147 MB，不带补丁中位 151 MB（各 5 次），**差别小于运行间波动**。

### 为什么撤销

- 整应用上**没有可测收益**；
- 只有两块时，如果 GPU 比较慢或屏幕是高刷新率，`nextDrawable` 可能让**主线程阻塞**等一块空闲纹理，也就是卡顿；
- 我们没有逐帧延迟测量来证明不会卡。

所以恢复成 3 块。**教训：一个"看起来能省内存"的改动，如果整体指标看不出收益，却带来无法证明安全的风险，就不要上。**
