# UI-01 主线程只做主线程该做的事

## 道理很简单

界面卡顿的最常见原因：**主线程被占住了**。主线程要处理输入、布局、绘制。只要它被某件事占了几十毫秒，用户就感觉到卡。

## 这个项目里的做法

- **磁盘、SQLite、解析日志、聚合统计，全部放到后台线程**（`spawn_blocking` 或专门的 worker）。
  界面只拿到结果。例如今日用量由后台摘要 worker 算好，界面只"借用"一个很小的 `Copy` 状态来展示。
- **界面不查系统时区、不读磁盘。** 时区在后台捕获；100 毫秒的画布轮询里不做这类调用。
- **别在每次渲染里调原生接口。** 窗口标题以前每次 render 都格式化版本号再调 `set_window_title`，
  现在记住最后一次请求的语言，稳定时直接跳过。
- **别在渲染里写控件值。** 滑块只在"确认边界"同步，渲染不每帧回写。

## 怎么判断卡的是不是主线程

对运行中的应用采样，看主线程（`com.apple.main-thread`）：

- 如果主线程几乎全是在 `mach_msg`/`RunCurrentEventLoopInMode` 等待（我们测到 83% 到 99%），说明主线程是闲的，
  卡顿要么在别的线程，要么是 GPU/显示，要么是测量时窗口根本没在前台（见 UI-04）。
- 如果主线程在 `draw`、`paint`、`layout` 这类函数里占了大量采样，才是主线程忙。

主题切换时的真实例子：v0.2.11 切换主题的主线程采样中，阴影栅格化占 6.4%；优化后降到 2.8%（见 CPU-04）。
注意这是占比，不是帧时长或 FPS，不能直接说"变流畅了多少"。

## 别踩的坑

- **后台读也不是免费的。** 主线程大部分在等待，不代表后台没有开销。后台 `today::load` 曾经每 30 秒占掉大量 CPU，
  主线程却一点都不卡——这种 CPU 会拖慢整机和电池，要靠 CPU-02 解决。
- **异步回调要检查"这一代还有效吗"。** 窗口可能已经关闭或换了屏，旧回调不应该再写状态。
