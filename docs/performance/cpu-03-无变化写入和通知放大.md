# CPU-03 无变化的写入和通知会自己放大

## 问题

有些 CPU 不是"算得慢"，而是**一个没有意义的动作触发了一串连锁反应**，而且连锁会反过来再触发自己。

典型的一条链（桌宠位置）：

```
窗口 bounds 通知 → 保存位置 → 版本号 revision +1
                  → 桌宠刷新 → 读设置/档案/图库 → 重建原生目录
```

窗口每次轻微抖动，哪怕位置和上次完全一样，也会走完整条链。

## 怎么发现的

画出"谁触发谁"的链，再数每一环的触发频率。只要某一环在"值没变"时也会触发下一环，就有放大。

## 怎么修的

1. **写入前先比较。** 保存位置时，如果物理像素位置和已保存的一样，就跳过写文件，也**不增加 revision**。
   注意：内存里的缓存还是要更新，只是不触发"有变化"。
2. **防抖要合并"最后的意图"。** 位置先按屏幕缩放换算成物理像素，不同位置静止 200 毫秒才提交；
   相同的目标**不重置计时**，否则连续同值通知会让保存永远不到期。
3. **通知只在展示内容变了才发。** 监控页每 3 秒读一次状态，原来每次都 `notify`，现在比较完整状态，相同就不通知。
   失败后恢复时即使数据相同也要通知一次，把错误提示清掉。
4. **先比便宜的键，再决定要不要复制大对象。** 原生服务每 40 毫秒克隆一次完整通知状态再比较 7 个字段；
   现在先拿一个小的 `Copy` 键比较，相等就直接返回。

## 别踩的坑

- **不能为了"不通知"就跳过业务该做的更新。** 同值的后台读取仍要更新"观测时间"，否则几分钟后会被判成过期。
- **"相同"的比较要覆盖所有会影响展示的字段。** 只比桌宠 revision 会漏掉 HTTP 拒绝计数这类变化。
- **测试要证明错误实现会失败。** 比如"永远不更新缓存"和"只在变化时更新缓存"两个错误版本，都应该让测试变红。
