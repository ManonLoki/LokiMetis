# GPU-01 纹理和图集的寿命

## 先搞懂几个词

- **解码像素（CPU）**：图片文件解码后的像素数组，在内存里。
- **图集（atlas）/ 纹理**：把图片上传给 GPU 后占的显存。多张小图会拼进同一张大纹理。
- **Scene（场景）缓存**：上一帧画了什么的记录，下一帧没变就直接回放。

同一张图在这三个地方有**三种不同的"主人"**，释放一个不等于释放另一个。

## 问题

1. 图库和桌宠共用同一张动图。隐藏主窗口后，这张图的显存还留在主窗口的图集里，因为"全局还有人在用"。
2. 皮肤预览换了一批内容，旧预览的 Asset 和图集里的旧条目还在。
3. 删除了一张图的"逻辑名字"，GPU 可能还在读它。这时如果把那块图集区域立刻让给新图，就会画出别人的内容。

## 怎么修的

### 窗口级退役（共享解码、独立纹理寿命）

分开判断"这个窗口里这张图的最后一个使用者走了吗"和"全局最后一个使用者走了吗"：

- 本窗最后一个位置退出 → 只删这个窗口里这张图的全部帧，并刷新场景；
- 全局最后一个才清 CPU 解码结果。

清理放到当前更新的收尾做，别在本帧已经提交了有效图元的时候就拆图集。
清理任务只带"弱引用 + 窗口 ID + 图片 ID"，不会让像素活得更久。

### 图集区域要等 GPU 用完才能复用

"删除名字"和"回收物理区域"是两件事。正确做法：

- 在第一次查询纹理时登记一个"编码批次号"；
- 逻辑删除立刻生效，但物理区域、纹理槽等**到当时已经提交的编码都完成或取消**才真正归还；
- 不能用"过两帧"或"下一次界面更新"代替"GPU 完成"，那都不是证明；
- 提交失败或被丢弃的编码也要能自动取消。

### 预览按"目录内容"退役

采用新目录时，以新目录里所有内容 ID 当作"保留集合"，不在集合里的才退役。
这样相同字节的新对象、元数据变化、多个卡片共用同一张图都能继续复用，不会每次离页清空全部缓存。

## 效果

用一张 512×512、120 帧的动图，同时在图库和桌宠里播放：

- 旧：图形内存（IOSurface）约 1.03 GB（dirty）；
- 修复后：两次可见采样都约 29 MB；隐藏主窗口后降到约 22 MB，恢复后约 24 MB。

条件：开发构建，进程寿命和后台负载没有完全统一，只能说"明显下降"，不能算精确倍数。

## 别踩的坑

- **别用全局删除兜底。** 窗口已关闭时，不要为了"保险"就全局清；会误伤别的窗口。
- **删了纹理要刷新缓存场景**，不然恢复时还在回放旧的图集位置。
- **测试里别拿 Metal 的 `contains` 当"是否驻留"。** 它默认返回 false，要查真实的图集 tile。
- **"最后引用"要看实际图片身份，不是逻辑 ID。** 同一个逻辑 ID 的新一代图不能阻止旧图被清理。
