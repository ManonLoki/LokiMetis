# 工程规则

本文件是本项目文件、中文注释、依赖、测试、文档事件及例外的详细事实源。当前为终端 GPUI 项目，不适用 Tauri/WebView/React/Mantine 规则；设计目录作为受管知识完整保留，按框架精确读取。

## 1. 适用范围与规则等级

硬规则保护架构、正确性、跨平台能力和交付可信度，违反必须修复；确需例外按第 6 节记录。默认规则用于可读性，有真实局部理由可偏离，不为普通组织选择增造 ADR。不得覆盖已有修改或为假想未来预建抽象。

## 2. 文件、模块与依赖边界

### 2.1 硬规则

- Core-first：宿主/接口无关的领域类型、语义校验、默认值、权限、幂等、工作流、状态转换、迁移、持久化策略和稳定领域错误必须在共享 core，经 core 自有类型 API 暴露。单一 GUI 也不例外。
- GUI 薄层仅装配运行时/驱动、解析接口语法、展示/交互状态、调用 core 并映射结果/错误；薄层按职责而非行数判断。多 core 调用间的业务条件/重试/编排提升为一个 core 用例。
- 文件/网络/外部进程/OS 具体驱动集中在明确能力模块，允许什么及结果如何改变业务状态由 core 决定；仅真实边界需要才定义运行时中立接口。
- 托盘、自启、单实例、热键、窗口偏好及页面会话属于 adapter；触发业务效果仍调用 core。单实例只恢复窗口，空热键合同不得占用系统键位；退出只释放 owned 资源。
- 已确认九字段由 GUI_APP_PROFILE 唯一保存，字段顺序与值不猜测、不遗漏；能力修改须明确授权，禁用能力不接入依赖、运行时模块、翻译键、设置开关、路由或专属资源。GPUI 深链接、updater 与通用 dialog 当前 unavailable。
- GPUI 主线程拥有原生事件循环；handler/render 不做磁盘/网络/外部进程阻塞。长任务有 owner、取消、有界队列和退出回收，不建嵌套 runtime 或无界 detached worker。偏好只在启动事件循环前有界读取，后台原子写，正常不可取消退出等待最后快照和日志刷新。
- GUI 身份、主题、设置、条件支持页和侧栏依照 profile 与 GPUI 标准。语言来自真实 sys_locale，未知回退英文；显式语言/三态主题优先，系统主题读取真实 WindowAppearance。首次/无效窗口居中 1440×900、最小 960×640，只恢复仍与显示器相交的尺寸/位置/最大化，不恢复隐藏/最小化/全屏。
- 控件动作绑定在语义控件本身，父 Card/行/单元格不得代理 Switch、按钮或链接；保留完整可访问名称与说明，回归覆盖控件和周围区域。
- 普通页面会话由原生根视图持有，在同进程跨页/隐藏/唤醒保留、退出重置；不写配置文件/数据库或镜像 core 权威状态。查询范围变化页码归 1，仅成功且当前非第一页为空才回退，加载/取消/错误不回退。
- 三候选 Logo 按稳定 candidate-1/2/3 原始顺序同时展示，选择前不检查或处理；选择后只验证/标准化选中项。可见构图/颜色改变须重新确认；精确母版、衍生图标与摘要进入 profile。品牌媒体保留来源/许可责任，未选赞助媒体不进入应用；展示支付材料不授权支付。
- 像素、密度、组件层级、事件所有权和可访问名称为硬规则；先匹配设计索引，产品明确批准的标准优先。专属偏离先确认并记 profile/ADR，不改写受管标准。
- 所有用户可见版本只带一个小写 v，机器事实保持原值；版本来源为根 Cargo，禁止手写会漂移的版本标题。
- 新必要第三方依赖先说明并确认，项目内显式声明与隔离；优先标准库/现有依赖，不假设全局包，未经明确请求不得全局安装。core 不依赖 GUI/宿主库，workspace 统一版本与依赖，成员使用 workspace 继承。
- 异步/错误/日志按 Rust 基线；日志不含秘密、业务载荷或 PII，使用稳定事件/错误类别，有界后台、滚动和退出刷新。unsafe 紧邻安全性解释，跨平台不默认单一 Shell/路径/权限模型。
- 人工维护、生成物与原样第三方内容明确隔离，不直接编辑生成物/第三方文件；声明的命令与验证必须真实存在。

### 2.2 默认规则

- 按职责、变化原因和领域概念拆分，不按类型数量、文件对称性或假想未来机械拆分。
- 一个文件围绕一个主要职责组织。总是一起变化且紧密协作的类型和函数优先放在一起。
- 出现独立领域概念、不同变化原因、平台边界或已经难以清楚维护时，应拆分文件或模块。
- Rust 代码超过 400 个物理行时进入建议重构区间；前端代码超过 500 个物理行时进入建议重构区间；其他人工维护文本超过 500 个物理行时进入语义复核区间。日常开发只报告硬超限，不因进入建议区间追加审查或阻断完成；明确发布且当次 `reviewSelection: enabled` 时，才集中检查业务是否高内聚、是否围绕单一职责，以及各部分职责是否相近，任一项不成立时按真实职责重构拆分。
- Rust 模块需要拆分为多个文件时，使用 `<module>/mod.rs` 作为目录入口，并把职责相近的子模块放入该目录，例如 `domain/mod.rs`、`domain/model.rs` 与 `domain/service.rs`；不得同时保留 `<module>.rs` 与同名目录，也不得为规避行数创建空壳转发层。
- 前端模块需要拆分时按功能或页面职责建立高内聚目录，调用方默认从具体组件、hook 或能力文件导入；不得为了对称性强制增加 `index.ts` 桶文件，也不得用 `export *` 隐藏真实来源。
- 不为每个类型或函数单独创建文件，不预建没有真实消费者的多层目录或扩展点。
- 禁止以 `utils`、`common`、`helpers`、`misc` 等兜底名称隐藏职责；共享代码必须使用真实领域或能力名称。
- 避免不能表达边界的 `manager`、`processor`、`handler` 等泛化名称。只有名称确实对应领域角色时才使用。
- 单元测试靠近被测单元；跨模块、CLI 契约和端到端测试放入独立测试目录。
- 只有转发作用且没有独立约束价值的模块应删除或合并。

### 2.3 分层代码行数门禁与通用文本上限

- Rust 代码：400 行及以内不因行数触发专项复核；401 至 800 行是发布审查可见的建议重构候选，但不阻断日常任务；800 行通过，801 行失败并强制拆分。Rust 多文件模块必须使用 `<module>/mod.rs` 目录结构，不能用同级 `<module>.rs` 加同名目录、空壳转发或压缩可读性规避门禁。
- 前端代码：500 行及以内不因行数触发专项复核；501 至 1000 行是发布审查可见的建议重构候选，但不阻断日常任务；1000 行通过，1001 行失败并强制拆分。前端拆分按功能职责保持目录高内聚，不强制 `index.ts` 桶文件。
- 其他人工维护文本：500 行及以内不因行数触发专项复核；501 至 2000 行是发布审查可见的语义候选，但不阻断日常任务；2000 行通过，2001 行失败并强制拆分。文档、非 Rust/前端脚本、配置、Skill、参考、模板和人工维护夹具适用此通用配置。
- 机械分类以文件后缀为准：`.rs` 使用 Rust 配置；`.astro`、`.cjs`、`.css`、`.cts`、`.html`、`.js`、`.jsx`、`.less`、`.mjs`、`.mts`、`.sass`、`.scss`、`.svelte`、`.ts`、`.tsx`、`.vue` 使用前端配置；其余 UTF-8 人工维护文本使用通用配置。
- 行数按 Node 校验器实现的通用换行符物理行语义计数，末尾换行不额外制造空行；不扣除空行、注释或声明，不得通过压缩可读性、合并无关语句或移除必要注释规避门禁。
- 建议重构或语义复核区间不改变日常任务结论。只有当次发布选择启用审查时才基于真实业务边界集中判断；内容不再高内聚、未围绕单一职责或各部分职责不相近时，返回开发循环按职责拆分并修正引用后再发布。
- Rust 超过 800 行、前端超过 1000 行或其他人工维护文本超过 2000 行时必须拆分；计划说明、审查结论、警告或 ADR 都不能把硬超限改判为通过。
- 工具生成且禁止手工编辑的锁文件/生成物，以及原样内嵌且明确隔离的第三方文件，不属于人工维护文件。这是封闭的范围定义，不是任意路径豁免；生成器、模板、补丁和维护说明仍按自身文件类型受分层规模治理。
- 当前原样第三方登记仅为`vendor/accesskit_macos/source-content.sha256`中的18项，清单摘要固定注册于行数检查的`verified_third_party.mjs`。仅清单和逐文件SHA-256均匹配、且路径无链接／越界时排除；额外文件、生成器、补丁、测试及维护说明照常计数。原样内容缺失或漂移必须失败，不能改成整个vendor目录跳过。
- 文件规模治理与职责判断同时成立：文件未达到对应建议阈值不证明职责合理，adapter 未超限也不证明其符合 core-first；语义边界仍按本节其余规则审查。

## 3. 中文代码注释

### 3.1 必需覆盖

- 所有人工维护的数据结构、接口、函数和方法都必须有符合业务语义的中文注释，不只覆盖公共 API。
- 数据结构注释说明业务角色、关键状态和必须维持的不变量；语义、单位或约束不直观的字段单独说明。
- 接口或 trait 注释说明职责边界、调用约定、输入输出、错误和副作用。
- 函数与方法注释至少说明其业务目的、主要处理逻辑或关键思路、重要前置条件与边界情况，以及返回结果、错误和副作用。
- 简单取值方法、构造器和薄转发函数也需要中文注释，但可以只用一句准确说明，不得为了满足格式编造复杂逻辑。
- 测试函数注释说明测试场景、关键条件、执行思路和预期结果。

### 3.2 内容质量

- 注释解释业务含义、设计原因、关键不变量和约束，不逐行翻译代码。
- 能通过更清晰的命名或结构表达的内容，先改进代码，再保留仍然必要的业务说明。
- 修改代码时同步更新相关注释。与实现冲突的注释按缺陷处理。
- 复杂算法说明不变量、阶段和取舍，不记录可直接从控制流读出的步骤。
- 非直观兼容处理、外部限制或规避方案必须说明来源、适用条件和删除条件，并链接对应决策、上游问题或官方资料。
- `unsafe` 代码块必须紧邻安全性说明，明确调用者保证、关键不变量及其成立原因。
- 禁止保留被注释掉的旧代码；历史交给版本控制。
- 不使用署名、时间线式修改记录或“由 AI 生成”等元信息注释。
- 中文术语在项目内保持一致；代码标识符继续使用英文。

### 3.3 临时标记与有限豁免

- `TODO`、`FIXME`、`HACK` 不得裸写，必须包含具体原因和完成或删除条件。当前任务不能解决时同步登记 `docs/TECH_DEBT.md`。
- 闭包和极短内联回调可以由所属函数的注释统一说明。
- 自动生成代码和内嵌的第三方代码豁免；宏展开结果由宏定义处统一说明。
- 纯声明型测试数据、静态常量集合和测试夹具可以通过所属模块或数据集说明统一覆盖。
- 豁免只消除逐项注释要求，不允许隐藏安全约束、数据来源或容易误用的业务语义。

### 3.4 机械存在性门禁

- Rust 下游必须保留 `.agents/skills/desktop-implement-change/scripts/check_rust_chinese_comments.mjs`，但只在本次变化需要、用户明确请求治理检查或发布/渠道硬要求时运行；日常开发和普通构建不为它增加独立步骤。它从 Cargo package 或 virtual workspace 根解析成员，扫描每个 package 的 `build.rs`、`src/**/*.rs` 和 `tests/**/*.rs`，并对人工维护的 `struct`、`enum`、`union`、type alias、trait、具名函数、关联函数、方法和测试函数检查声明自身是否具有紧邻、包含至少一个汉字的 outer doc comment。attribute 可以位于文档注释与声明之间。
- Rust 门禁不要求逐字段、局部变量、闭包或宏展开产物；非直观字段仍按第 3.1 节语义复核。模块注释、父项注释、普通 `//`、纯英文文档注释或字符串中的中文不能替代声明自身的证据。
- “包含至少一个汉字”只证明注释存在且归属正确，不证明内容有业务意义；语义质量仍按第 3.2 节由人工或 Agent 复核。门禁不得自动生成或批量补入“保存变量供当前逻辑使用”“执行处理逻辑”等套话。

## 4. 文档规则

### 4.1 单一事实来源

- 每项事实只能有一个权威来源。其他文档可以摘要并链接，但不得复制一份会独立演化的规则。
- 文档与代码、配置或测试冲突时，必须调查真实行为并在同一任务中修正，不能默认任一方正确。
- 文档中的命令、路径、配置项、版本和能力必须来自真实仓库，不得虚构或把计划中的能力写成已实现。
- 未确认信息明确标为“待确定”，未运行检查标为“未执行”，未实际验证的平台或行为标为 `Unverified`。
- 产品目标、边界、约束或成功标准变化时更新日期最新的 Product Spec；长期重要、难以逆转的决定和硬规则例外写入当日 ADR。范围清楚的日常实现不为每项需求创建 ADR。Product Spec、ADR、Changelog 或 Work Plan 被自身事件独立触发时，必须记录相关稳定 `change_id` 与 `$desktop-manage-version` 只读计算或提交结果中的 `required_version`；版本变化本身不得触发或补造项目记忆。
- Product Status 只在重要阻断、跨会话交接、真实渠道发布后的记录阶段或用户要求时更新；Work Plan 只在用户明确要求、跨会话交接或发布/高风险协调确有必要时维护；Verification 只保存真实渠道发布后追加的发布/候选验收事实，或独立回顾性人工复核/长期审计证据。
- 普通缺陷修复、不改变可观察行为的纯重构、格式整理、测试补强和内部清理本身不触发 Product Spec、ADR、Product Status、Changelog 或 Verification；结果只在最终回复和测试/CI 中报告，不写“不适用”占位。已有 TECH_DEBT 条目在问题消除后必须恢复真实状态，但不新增修复流水账。
- 构建请求、执行、成功、失败、重试、全量单元测试结果、产物路径/摘要/签名状态，以及候选 E2E、完整验收、状态更新和就绪复核，都不触发 Product Spec、ADR、Changelog、Product Status、Work Plan 或 Verification。候选事实只写入忽略的 `release/` 原子集合、manifest 声明的相邻证据和最终回复；Git 发布在本地默认主分支与 tag 复读成功时结束，下游受跟踪周期状态在下一条开发分支复核这两条 ref 后复位。真实渠道分发和回顾性审计各自按独立事件记录，不改写已完成的 Git 发布事实。
- 本项目中英文名称已确认；许可证和 locale 字面文本分别使用中文/英文名称。未来改名按身份 Skill，精确名称替换不得改变法律条款。
- 根 `release-notes.json` 是 本项目共用的双语发布更新日志事实，不是按日项目记忆，也不替代 `docs/changelog/`。它只在准备首个正式发布时创建，使用 `schemaVersion: 2`；每个功能优化或问题修复条目把非空 `zh-CN` 与 `en-US` 文案绑定为一个翻译对，任一语言缺失、空白或同语言重复都失败关闭。每次正式发布前，根据上一次正式发布版本到当前发布源码的真实差异更新当前版本，按最新在前只保留包含当前发布版本在内的最近 10 个实际发布版本条目，每版“功能优化”和“问题修复”各不超过 10 个双语条目。普通缺陷修复即使不触发 Changelog，仍应进入对应发布版本的“问题修复”；失败发布可替换同版本条目。更新日志字节变化始终要求重新提交；终端下游还必须重新构建和验收候选，Harness 源则重新执行 Git 源码发布复核，不虚构产品候选。
- 候选构建不得生成或改写更新日志，只读校验已提交的 schema v2 双语日志；GPUI 构建注入与资源 map 嵌入相同字节，实际应用及最终 DMG 内资源/manifest 摘要不一致即阻断。
- 同一维护任务若另外改变产品目标/边界/约束/成功标准、引入长期决定或硬规则例外、形成重要阻断/交接、完成真实渠道发布，或另行进入回顾性人工复核/长期审计，才按该独立事件更新对应记忆。候选验收阶段只写忽略的 `release/` 原子证据；任务被称为“修复”或“重构”不能绕过相应的安全、发布或记录要求。
- 除上述维护排除外，用户或维护者可感知且符合 Changelog 资格的真实行为/流程变化写入当日 Changelog。修改代码或规则时仍须同步受影响的权威设计文档和测试；同步事实不等于创建项目记忆。
- 修改工程规则时，同步检查 `AGENTS.md` 的入口路由、相关 Skill、本文件和适用的机械检查；任务专属细节只在其唯一事实源中校验，不得为了通过检查复制回根入口。
- 删除或替换规则时清理失效入口、链接和摘要，避免旧规则继续进入 Agent 上下文。

### 4.2 固定职责

### 4.3 编写、拆分与归档

- `AGENTS.md` 是启动路由器，不是全部规则的镜像。它必须保留启动门禁、按任务渐进读取、始终生效边界、非空 Skills 地图、非空约束地图和最小闭环；命中任务后再完整读取精确 Skill 与事实源，不预先加载同类全部 Skills 或无关项目记忆。
- 根 `AGENTS.md` 的 UTF-8 字节数不得超过 20,000，行数不得超过 120。新增详细初始化、GUI、依赖、构建、发布或验证规则时，正文写入既有唯一事实源或对应 Skill，根入口只增加确有必要的路由或跨任务摘要。
- 标题和首段先给结论，再补充原因、边界和证据。
- 规则必须说明做什么、何时适用、如何验证和允许什么例外，避免无法判定的“适当”“尽量”或“一般来说”。
- 示例必须标明是规范示例、占位示例还是真实验证结果，不得混淆。
- 内部链接使用相对路径；外部技术结论优先链接官方来源，并记录核对日期。
- 日期统一使用 `YYYY-MM-DD`；状态使用仓库规定的固定词汇。
- 文档不保存被删除内容的注释版本；历史交给版本控制、决策记录、验证记录或变更记录。
- 所有文档同样受 500 行建议区间与 2000 行硬上限；日常只强制硬上限，501–2000 行只在当次发布 `reviewSelection: enabled` 时集中复核。该复核优先识别独立主题，职责不再单一或相近时拆为有明确职责的文档，并由原入口保留目录和链接。
- `README.md`、`AGENTS.md`、方法论和项目记忆没有长文档例外；拆分必须保持每项事实的唯一来源、稳定入口、历史失败证据与人工复核事实。
- Product Spec、Product Status 和 Work Plan 只有触发条件满足时才写入；同一天只更新各自唯一日期文件，不得为同一天创建第二份。
- 需要在新自然日写入上述记忆时，先读取前一份，将仍有效事实、未完成事项和当日变化综合重写为完整当前快照，不得只写增量。
- 产品状态日期文件始终重写为当日完整当前状态，不累积流水账。
- 工作计划日期文件只保存当日完整当前计划。结果进入状态、验证、决策和变更记录；旧日期文件随即删除，历史由 Git 版本控制承担，不另建 `docs/archive/work-plans/` 副本。
- 同一未发布日期文件内，已被后续决定完全替代且会污染当前检索的规范描述可以合并为最新有效表述；合并必须新增 ADR 记录范围、理由、风险和恢复依据，并保留仍有效的决定编号、人工复核事实与失败证据。
- 日期文件名使用紧凑日期 `YYYYMMDD`，正文日期仍使用 `YYYY-MM-DD`。同一天不得创建第二个产品规格、产品状态、工作计划、ADR 或变更记录文件。
- 涉及产品边界、长期规则、硬规则例外或完整候选复核时先读 ADR 索引与最新日期 ADR；日常开发只在受影响区域存在相关决定时读取。只有最新条目显式引用仍有效的旧日期事实时才继续追溯。

## 5. 测试组织

- 行为变更用本次相关非空单元/回归覆盖成功和最高风险失败；业务先 core 测试，再 adapter 输入/映射/错误/生命周期。公开业务操作可追溯“GUI 操作 → core API → core 测试”。布局/宿主机制说明其 adapter 专属性。
- 修复增加可复现回归；无法合理单测时说明替代验证和风险。测试验证可观察行为，不镜像实现或对无关细节耦合。
- 测试确定、隔离、可重复，临时目录不依赖网络/当前时间/随机顺序/真实 HOME 数据。宿主初始化检查恢复应用拥有的登录项、偏好和快捷键状态；不重定向 HOME。
- 测试名称英文 snake_case、中文注释；小夹具靠近测试，大夹具 tests/fixtures，来源明确只读。文件规模按自身类型硬上限，跳过/未执行项目如实报告。
- 远程能力另测试未配置/未同意/撤回时零出站，以及方法/允许地址/字段/重定向/大小/超时/取消/脱敏中的最高风险边界；远程功能须独立产品批准与安全配置。
- 日常直接实施，仅本次必要测试；不因多模块/复杂或可并行自动追加计划、全仓检查、构建、冒烟、E2E、Verification 或人工复核。
- 显式候选构建运行全 workspace/all-targets/all-features 非空测试，失败/零测试阻断。默认锁策略 ignored 不用 --locked；显式 tracked 时先核对锁跟踪且不忽略，再冻结解析，清单漂移失败关闭。
- 真实环境失败才用环境 Skill 单次恢复重试，不预检；任何全局安装仍须用户明确请求。实际提交前才检查仓库身份/模板，只写必要 local，不改 global/system。
- 新功能/独立修复写入前走 Git 生命周期；版本由版本 Skill 分类、完成且相关测试通过才 apply。发布、审查、候选、签名和验收遵守 RELEASE/Policy，不混入日常工作。中性 debug 检查不等于产品验收。

## 6. 规则例外

硬规则确需例外时，先由负责人明确批准并写当日 ADR，记录原规则、原因、范围、风险、验证及恢复/删除条件，再实施。无批准或 ADR 不继续；行数硬上限不能通过 ADR 改判为通过。规格不同答案会改变产品边界时先确认，普通实现细节不增造会议。

## 7. 机械检查边界

pnpm run validate 仅运行保留的文件硬行数、Rust 中文注释存在性与 core-first 检查，不证明语义质量或发布验收。建议规模、TODO/FIXME/HACK 与非必要语义审查只在当次发布 reviewSelection=enabled 集中复核；不能自动追加到日常任务。项目没有上游专用的脚本语言禁令。
