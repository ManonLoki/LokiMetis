# 记录长期决定

读取存在的 [ADR 索引](../../../docs/adr/README.md) 与最新 ADR，以及 [工程规则](../../../docs/ENGINEERING_RULES.md) 的记忆、快照和规则例外章节。只记录已经确认的决定；Harness 源只记录自身工程，不接收下游产品业务。

## 执行

1. 核对决定、确认来源、适用范围和真实关联事实。复用当前授权，不把提议写成已批准、已实现或已验证。普通实现细节、缺陷修复、行为保持重构、格式、测试补强、内部清理和版本变化不单独触发 ADR；明确不可例外的硬门禁不能通过 ADR 豁免。
2. 检查 Git 根、分支和既有修改。记录直接调用也先遵守 `$desktop-implement-change` 的写入前门禁；由调用方维护同一生命周期，已有调用上下文直接复用其分支、版本分类和提交责任，只完成记录后返回，不重新执行完整实施流程。
3. 已初始化下游复用相关稳定 `change_id` 与版本门禁返回的 `required_version`；缺失时按原事件分类由 `$desktop-manage-version plan` 只读取得，不为 ADR 提升版本。Harness 遵守自身记忆和时间版本约定，不提前正式取号。
4. 首个真实 ADR 事件触发且索引缺席时，按工程规则建立项目自己的中立索引，不复制 Harness 决定、批准或历史；没有合格事件不创建目录。按索引在唯一自然日 `YYYYMMDD_ADR.md` 顶部写入稳定 `ADR-YYYYMMDD-NNN` 条目，包含状态、关联需求、背景、决定、影响、理由、风险、真实验证或替代验证、恢复/调整标准。精确注明取代范围，部分取代保留仍有效约束。
5. 同日更新现有文件；新日先读取前一份，综合仍有效决定为完整快照。完成新快照和索引核对后，才按索引删除被完全承接的旧日期文件；不改历史归档，不删除失败或人工验证证据。Harness 过期决定治理另走 `$desktop-curate-harness-memory`，不传播到下游。
6. 同步真正受影响的权威文档；Spec、Status、Plan、Changelog、Verification 只由其独立事件触发，未触发不写占位。完成必要链接/差异检查后返回原实施流程。

## 输出

报告 ADR ID、确认来源、文件、决定与取代范围、关联变更和版本事实，以及实际检查、未验证事项与恢复条件。
