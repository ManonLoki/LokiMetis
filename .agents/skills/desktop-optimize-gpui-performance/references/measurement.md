# 测量合同与证据强度

记录源码/dirty 摘要、release/dev profile、工具链、OS/硬件/GPU、DPI、窗口尺寸、可见性、桌宠/动画/素材状态、数据量、冷/热启动、预热、采样长度、后台 helper 和重复次数。固定可执行/PID身份，不把重启后新进程接到旧样本。采样原始数据放任务隔离区；候选事实才进忽略的 `release/`。

至少区分：

- CPU：进程累计 CPU 时间差 / 同一单调时间窗；交代百分比按单核还是整机，说明是否包含子进程/coalition。
- 内存：RSS、当前 physical footprint、生命周期 peak、allocator 活跃/保留、CPU 像素和 GPU 驻留分别计。不要用旧 peak 判断当前释放，也不要把 RSS 降低直接解释为显存减少。
- UI：输入到呈现、帧间隔、layout/paint 时间与长尾；没有逐帧采样就不声称改善卡顿分位数。
- 启动/查询：冷/热、索引有无、缓存是否命中分别测；微基准只说明该机制成本。

同条件交替 A/B、多次采样，报告分布与噪声，不只选最优一次。改变素材、工作负载、helper 或 renderer 的对照不能归因于单个优化；和 Tauri 比较需匹配完整功能/进程边界。合成短窗、单机结果明确限制，不外推长跑或其他 OS。

无收益就撤销机制，不因微基准好看保留。已有 GPUI 案例曾撤销 allocator pressure-relief 和把 Metal drawable 数从 3 降到 2 的尝试：整应用未形成可靠收益，后者还有阻塞风险。它们是需要复测的反例，不是所有机器都禁止的 API。

标准库及系统已有工具优先；新 profiler/CLI 只有当前测量确需且获授权才安装，按全局工具政策核对路径与版本。Harness 自动化维持 Node 标准库；下游既有 Python/系统采样脚本按自身规则复用，不复制成上游 Python 步骤。
