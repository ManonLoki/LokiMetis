# 定义产品

只在产品边界需要决定时，把真实问题转化为经确认且可测试的范围；不要把普通实现细节升级成产品会议。

## Harness 源门禁

先解析当前规范根目录。若根目录同时包含 Harness 专用 `Version.md` 和活动 `.agents/skills/desktop-instantiate-project/SKILL.md`，当前就是 Harness 模板源，不是终端下游；必须在读取、整理或写入任何产品需求前停止。不得把产品目的、用户场景、输入输出、业务规则、成功标准、产品专属 UI/文案/数据、远程地址、凭据或发布需求写入 Harness 的 Product Spec、ADR、Changelog、代码、资产或临时计划，也不得替用户在源根执行产品实现。只告知用户先完成 `$desktop-instantiate-project`，或切换到已存在下游的唯一 Git/项目根目录，再重新提出产品需求。Harness 工程规则、Skills、验证器和中性资产自身的维护不受此门禁阻止。

## 工作流程

1. 通过 Harness 源门禁后，只在当前终端下游 Git working tree 完成范围设计；不为范围讨论建立额外并行工作流。
2. 读取存在时的最新 Product Spec，以及与当前问题直接相关的 Product Status、最新 ADR 和中性 scaffold 约束；不默认加载全部历史。中性结构不是产品意图证据。
3. 提取核心用户、首要消费者、真实场景、输入、输出和痛点。把接口/宿主无关的业务结果与 GUI 窗口、IPC、托盘等宿主机制明确分开；不得在 GUI adapter 中定义会与 core 静默分叉的业务规则。只询问不同答案会改变产品边界的缺失信息，非阻断未知项标为 `待确定`。
4. 写出一个聚焦结果、不绑定实现技术的目标，并定义 `包含`、`不包含`、假设、约束、可靠性要求和可观察成功标准。凡接口/宿主无关的行为都以 core 用例、稳定领域结果和统一错误表达；接口或平台特有机制可以留在适配器，但其业务效果仍委托 core。
5. 对拟议能力执行范围闸门：只有缺失会使核心闭环无法完成或可靠性不可接受时才进入当前范围。
   普通缺陷修复、不改变可观察行为的纯重构、格式整理、测试补强和内部清理不构成产品范围变化，不调用本 Skill；只有调查确认批准的产品目标、边界、约束或成功标准确需改变时，才继续第 6 步。
6. 新产品首次确认或现有产品目标/边界/约束/成功标准变化时，创建或更新当天 Product Spec。该决定长期影响后续工作，因此在当天 ADR 写一个条目；同日复用现有文件，新日从前一份综合仍有效事实。
7. 只有出现重要阻断、跨会话交接、下游真实渠道发布或用户要求时才更新 Product Status；候选构建、E2E、完整验收和就绪复核只把事实写入忽略的 `release/` 原子集合及最终回复。不要为了范围确认自动创建 Work Plan、Verification 或 Changelog，普通维护任务也不得反向生成这些记忆。
8. 范围确认后，为每个进入实施的新功能建立稳定 `change_id`，调用 `$desktop-manage-version plan --kind feature` 只读取得 `required_version`，并把二者写入被本次范围变化触发的 Product Spec；若用户另行批准 Major，则使用 `major` 与精确值。范围确认后直接交给 `$desktop-implement-change`。只有用户明确要求持久计划、跨会话交接或发布/高风险协调确有必要时才调用 `$desktop-plan-change`；构建、完整验收和发布都必须由用户显式请求或对应硬要求单独触发。

## 输出规则

- 保留明确非目标，区分当前范围和未来候选。
- 未经用户确认，不得把规格标记为 `Approved`。
- 不选择额外技术，不创建业务实现，也不预建未触发的项目记忆。
- 最后列出仍未解决的边界决定和下一项直接实施行动；不要额外创建流程档位。
